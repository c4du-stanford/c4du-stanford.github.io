Troubleshooting

The names here are examples. pat, pats-claude-code and pat__cosci-notes stand for your handle and private lab, and OWNER/SHARED-REPO (key shared-repo, folder owner__shared-repo) for a shared lab's repo. Replace them with your own (cosci status shows them). Most problems show first in a turn's footer or in cosci status.

GitHub refuses your credentials

At install, cosci join or cosci status --fetch, you see cosci: could not clone OWNER/SHARED-REPO: … Authentication failed …, with what to check.

In a session, opening a thread or recording stops with freshness-fetch-failed and auth_ok: false, or a footer says → not pushed yet: … your git credentials for origin were refused or are not set up …. In the end-to-end run the session's environment lacked credential variables the person's shell had; cosci returned the error at once, wrote nothing and did not hang.

cosci never prompts, so git must reach GitHub on its own. If you signed in to GitHub during the guided install and kept that sign-in for CoSci only (the default), cosci's own git commands use it and your other git commands do not. Then check from cosci, with cosci status --fetch, and check the sign-in with ~/.cosci/gh/bin/gh auth status (or gh auth status if you used your own gh). If it is no longer signed in, run the installer again (download it from the install page): it offers the sign-in again.

Otherwise cosci uses git exactly as you have set it up. Check outside cosci:

git ls-remote https://github.com/OWNER/SHARED-REPO HEAD
git -C ~/.cosci-data/pat__cosci-notes fetch origin

If either asks for a username or password or fails, fix git's credentials (cosci needs no change) in one of these ways:

  • The GitHub CLI: gh auth login, then gh auth setup-git.
  • An HTTPS credential helper with a personal access token. git config --global credential.helper store keeps the token in plain text in ~/.git-credentials. On a shared machine, prefer the system keychain helper or cache (memory only). A cache helper must already hold the token, so run one git fetch by hand (it asks for the token once) before starting cosci.
  • An SSH key added to your GitHub account. Check it with ssh -T git@github.com, then re-run the install line with --protocol ssh. Existing clones keep their original URL; for those, run git -C <clone> remote set-url origin git@github.com:<owner>/<repo>.git.

A Claude Code session's cosci server inherits the environment you start cosci from, so variables your shell sets for git (such as GIT_ASKPASS) reach it, as verified in the end-to-end run. With Codex this is unchecked: use credentials git finds through its own configuration (a helper or an SSH key).

Turns say "not pushed yet"

The footer adds a line like:

→ not pushed yet: saved on this machine only, not on GitHub (origin could not be reached; check the remote and the network, then retry). The next cosci write pushes it

The turn is committed in your clone; only the push failed, for the reason in the parentheses. The next cosci write pushes everything waiting; until then cosci status shows the repo as (1 ahead, 0 behind) (or more). If the reason names credentials, see the section above. A repo with no remote (local only) never pushes and never says so.

A push was rejected

If someone pushed to the same repo first, cosci silently fetches, replays your commits on theirs and pushes again, a few times if needed. It stops only when you both changed the same file incompatibly. Your commit stays as it was and cosci reports push-rebase-failed, with the commands to look:

git -C ~/.cosci-data/owner__shared-repo status
git -C ~/.cosci-data/owner__shared-repo log --oneline origin/main..HEAD

Reconcile by hand (or ask whoever else writes that repo), then make any cosci write to push again.

git identity is not set

An append fails with no git identity or Committer identity unknown. The installer and cosci join set a commit name and email on each repo cosci makes or joins (the install summary's commits line shows them), so this happens in a repo set up some other way. Re-run the install line with --git-name "Pat Example" --git-email pat@example.org (it sets them on every data repo), or set them for one repo:

git -C ~/.cosci-data/pat__cosci-notes config user.name "Pat Example"
git -C ~/.cosci-data/pat__cosci-notes config user.email pat@example.org

The cosci tools or slash commands do not appear

The agent has no cosci tools, /cosci: completes to nothing, or cosci open-thread is treated as ordinary text.

cosci attaches only to sessions started with cosci (Claude Code) or cosci codex (Codex). A claude or codex you started yourself, even in the same directory, has none of it. Codex has no slash commands; type cosci status there. After cosci update, start a new session: tools and skills are read at session start. To see what cosci passes to the agent:

cosci --dry-run
cosci codex --dry-run

For Claude Code you should see --mcp-config ~/.cosci/run/mcp-<pid>.json, --plugin-dir ~/.cosci/plugin, --append-system-prompt-file … and --settings …. For Codex, -c mcp_servers.cosci.command=… and -c developer_instructions=….

If /mcp in Claude Code shows cosci failing, run the server by hand with empty input; it should exit silently:

COSCI_CONFIG=~/.cosci-data/config.yml COSCI_HANDLE=pats-claude-code python3 ~/.cosci/mcp/server.py </dev/null && echo "server ok"

A traceback here is the real error; the next two sections cover the usual ones.

The install page or the installer stops before installing

  • The install page shows 404, or GitHub keeps asking you to sign in. The page opens only for GitHub accounts with access to the private repo stanford-developers/rubin-cosci-install; Stanford members sign in with Stanford. Ask the person who invited you to add your GitHub account.
  • On a Mac, the setup window looks older than expected. You downloaded twice, and the newer copy opened as Install CoSci 1 while the pasted line ran the older Install CoSci. Close the setup window, eject both in Finder's sidebar, open the newest CoSci-Install.dmg in Downloads, and paste the line again.

Each of the following stops before writing anything (no ~/.cosci, no ~/.cosci-data); most say nothing was installed.

  • does not match its checksum: the file you ran is not the published one, usually because the download or the upload to the Rubin Science Platform was cut short. Download it again from the install page (and upload it again); if it keeps failing, tell the person who maintains cosci.
  • Could not reach the release (when installing with git clone from https://github.com/stanford-developers/rubin-cosci-install): git could not sign in to GitHub with access to that repo. Sign in with gh auth login (and gh auth setup-git for git), or ask to be added to the repo. Or download cosci-install.sh from the install page instead, which needs no git access.
  • is not an https URL: COSCI_INSTALL_URL (or --install-url) names a plain-http address. Only https is accepted, apart from plain http to 127.0.0.1 or localhost.

After installing from the install page, cosci update fetches the newest release through git with your GitHub sign-in. If it can't reach the release, it stops the same way and leaves your harness and data repos as they were: fix the sign-in as above, or download the newest installer from the install page and run it; your labs and settings are kept.

Starting a shared lab fails

--create-shared OWNER/SHARED-REPO stops with already exists on GitHub when someone has created it. A shared lab's repo is created once, so join it with --shared OWNER/SHARED-REPO (its admin gives you write access).

It stops with could not create the project's shared repo when your login may not create repos under that owner. Ask an organisation owner to create it as an empty private repo and give you write access, then run cosci join OWNER/SHARED-REPO (or install with --shared). If you may create repos elsewhere, you can also create the empty repo yourself with gh repo create OWNER/SHARED-REPO --private and join it. cosci does not send invitations: give colleagues write access on GitHub.

Both are refused before anything is written. The default install keeps your private lab on this machine and needs no GitHub account. Creating a repo on GitHub (--create-private, --create-shared) needs the GitHub CLI (gh), signed in with gh auth login.

A second lab is refused

Joining a shared lab stops with cannot add … as a shared repo here: … is already the key of … when another configured repo already has that key: another lab's repo with the same name (OWNER-A/data and OWNER-B/data), your own private lab, or the reserved name manager. A shared lab must have the same key on every machine, so cosci will not rename the new one. Free the name by removing the other entry from config.yml (its clone stays on disk) or renaming that entry's key by hand (citations made under the old key then stop resolving), then join again; see configuration.

cosci is not found

The installer links ~/.local/bin/cosci. If your shell says command not found, ~/.local/bin is not on your PATH yet. The installer adds it in your shell's startup file (~/.zprofile for zsh, ~/.bash_profile or ~/.bashrc for bash), which only new terminal windows read: open a new one. For another shell, or after --no-path, add export PATH="$HOME/.local/bin:$PATH" to its startup file yourself, or run ~/.cosci/bin/cosci directly. The launcher line of cosci status says whether the link exists and is on PATH.

PyYAML is missing, or Python is too old

The error ends in No module named 'yaml' or says cosci needs Python 3.9 or newer. cosci, its server and the hooks run with CoSci's own Python environment, ~/.cosci/venv, which has PyYAML. They use another Python only when COSCI_PYTHON is set, or when ~/.cosci/venv/bin/python is missing (then the python3 on your PATH). Check it:

~/.cosci/venv/bin/python -c "import sys, yaml; print(sys.executable, sys.version.split()[0], yaml.__version__)"

If that fails, run the installer again (download it from the install page): it makes the environment again when the old one no longer runs, and adds PyYAML. If you set COSCI_PYTHON, that Python must have PyYAML itself ($COSCI_PYTHON -m pip install PyYAML); cosci installs nothing into it.

The installer can't make CoSci's Python environment

The installer stops with could not make CoSci's Python environment. It makes ~/.cosci/venv with python3 -m venv, and some Linux systems ship Python without that part. On Debian or Ubuntu, install the python3-venv package (ask your administrator if you have no root), then run the installer again. Or set COSCI_PYTHON to a Python 3.9 or newer that already has PyYAML, and cosci uses that one as it is (see the install reference).

The guided install: a sign-in or a lab does not work

  • On a Mac, the setup window does not open. The installer then says so and asks in the terminal instead; the questions and the result are the same. It opens the window only when pywebview is installed in CoSci's own Python environment. If the window opened behind another one, look for CoSci setup in the Dock. To skip the window, add --terminal.
  • It asks nothing. The installer asks only when it runs in a terminal. Run from an agent, a script or with --yes, the options decide. Run the line yourself in a terminal to be asked.
  • The GitHub sign-in did not complete. The one-time code was not entered at https://github.com/login/device, or not in time. The install goes on without GitHub, with your private lab on this computer. Run the installer again and answer yes to sign in; it keeps what was installed.
  • GitHub says … can't see …. Either the lab's name is mistyped, or its owner has not added your GitHub account yet. Ask the owner to add you as a collaborator; if they have, accept the invitation at https://github.com/notifications and type the lab again. Press Enter to skip it for now and join later with cosci join OWNER/SHARED-REPO.
  • … can read … but not write to it. Every recorded turn is pushed to the lab, so you need write access. Ask the lab's owner for it. The installer asks whether to join it anyway, read-only for now (default no).
  • An agent's sign-in did not finish. The installer shows the command to sign in later (claude auth login, or codex login). Run it before you start a session with cosci; the agent keeps its own sign-in.

Nothing is being recorded

Replies arrive without a → committed … footer. Ask the agent cosci status:

  • No thread is open. Recording starts when one opens: cosci open-thread <name>.
  • The band is closed: cosci open-band. The band belongs to one session; closing it in another window does not affect this one.
  • The agent reports refusing to append: the turn body is exactly the identity 'claude-code', not a reply. It put its own name where the reply goes; tell it to record again with your message as human and its reply as agent.
  • You typed cosci quiet earlier: footers are hidden but turns still land. Run cosci unquiet and check git -C ~/.cosci-data/pat__cosci-notes log --oneline -5.

If a thread is open, the band is open and the log is not growing, type /cosci:record (or cosci status in Codex) and read the error the agent reports.

cosci share is refused

cosci share refuses, saying why, when:

  • The current thread is not stored in your private lab. Open a private thread first (cosci open-thread <name>).
  • You have joined no shared lab (cosci join OWNER/SHARED-REPO), or several and you did not say which (cosci share <id> --to <key>).
  • An id is not in your private knowledge base. Copy ids from /cosci:context; they look like cosci-notes/project-setup/priors-in-config-yaml.
  • The statement's text names you or another configured person, your home folder, or a private lab or thread. That text stays private by design. Restate the point without the private name in a thread, let cosci learn it, and share the new statement.

Sharing a statement already shared is not an error; nothing new is written, and the result says so.

A locator cannot be opened

permission_denied with reason repo-not-configured means the locator points into a repo this machine does not have, usually another person's private lab. There is nothing to grant; you can read what they shared with your lab. For a repo of yours or your project's, add it with cosci join OWNER/SHARED-REPO [--private].

Plain permission_denied with a remedy such as cosci grant shared-repo read means the repo is here but this thread may not read it. Type the grant if it should.

Learning reports an error, or never runs

cosci status shows each repo's last learning pass, and on its learn line the last failure:

    cosci-notes        private   pat/cosci-notes                  ~/.cosci-data/pat__cosci-notes  (up to date)
                     learn: learned from 4 turn(s) at 2026-10-20T09:01:43Z; commit 4b5a33ad586f, pushed
  • never ran here: no pass has started for that repo. A pass starts only after a call on an open thread stored there, at most every 30 minutes.
  • off (… is not on PATH …) or learn off: the learner's command is missing or learning is off. Install it, or choose another with "learn": "claude" / "codex" in ~/.cosci/settings.json.
  • error … claude reported an error or exited with …: run the command once by hand (claude -p "hello", or codex exec "hello") to check it is signed in and works. The next pass retries.
  • error … Not logged in · Please run /login while claude -p "hello" works in your shell: you sign Claude Code in with the CLAUDE_CODE_OAUTH_TOKEN environment variable. Claude Code does not pass it to MCP servers it starts, so the learner (started by the cosci server) runs signed out (Claude Code 2.1.304). Sign in once with claude and /login, which stores the sign-in in Claude Code's own credentials file; the learner then uses it. cosci improve, which you run from your shell, is not affected.
  • learned …; commit …, committed locally, not pushed yet: the knowledge-base commit is in your clone but not on GitHub, usually for the reason in the first section.

Failures are logged in ~/.cosci-data/learn.log and never affect your session. To stop learning, set "learn": "off" in ~/.cosci/settings.json and start a new session.
