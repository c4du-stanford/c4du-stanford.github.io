Threads and sharing

Threads

A thread is a named conversation. Names are lowercase letters, digits and hyphens.

cosci open-thread project-setup

cosci open-thread makes it the current thread for this session, creating it if the name is new. From then on every reply the agent gives you is appended to the thread and committed on your machine. For a lab on GitHub the commit is then pushed; a local-only lab keeps it on this machine. cosci new-thread <name> does the same but refuses a name that already exists, so it never joins an old conversation.

cosci list
cosci status
cosci catchup
cosci close-thread
  • cosci list shows the active threads.
  • cosci status reports the current thread, the band (whether it is recording), its permissions and the last few turns.
  • cosci catchup, for returning days later, shows the status, recent turns in excerpt, and the latest human and agent turns in full.
  • cosci close-thread returns you to an ordinary, unrecorded session.

A thread is stored in one lab: by default your private lab, where it is yours. To store it in a shared lab, name the lab by its key: cosci new-thread shared-repo/survey-plan (cosci open-thread takes the same form). A thread stored in a shared lab is readable by every member of that lab.

Its folder, discussions/<thread>/, holds:

  • the turns, in numbered files (project-setup-0.md, then -1.md, and so on)
  • a small telemetry file per chunk
  • the thread's permission file, <thread>.meta.yml

When a chunk passes about 40 KB or 50 turns, the next append starts a new one and ends the old file with → continued in project-setup-1.md. Nothing already committed is rewritten.

Turns

A turn is one ## block in a chunk file: your messages are human turns, the agent's replies agent turns. cosci ends each agent turn with two lines:

[runtime: harness=claude-code harness_version=2.1.304 model=claude-sonnet-5-5 mode=careful runtime_contract=omit-unknown]

[committed: 8d11af1d3dfe files=2]

The [runtime: ...] line records which agent, version and model produced the turn. A value the agent does not expose is left out; cosci never guesses one. The [committed: ...] stamp holds a 12-character hash of the turn's own content and the number of files in its commit. A hand-edited turn no longer matches its stamp, and replaying an identical turn returns the original commit and records nothing new.

After each append the agent shows you the recorded turn, with the runtime line in plain words, and then the footer:

## Tuesday October 20 2026 · 1:57 AM PDT · pats-claude-code (claude-code)

Understood: lens-model priors live in config/priors.yaml, and no notebook hard-codes them.

⚙ Claude Sonnet 5.5 in Claude Code 2.1.304 · careful · effort unavailable

[committed: 8d11af1d3dfe files=2]

→ committed 1c4444f to discussions/project-setup/project-setup-0.md

The turn you see is the one in the file. A local-only lab shows only the committed line. When a push to GitHub has to wait (offline, or GitHub refused your credentials), a second footer line says → not pushed yet: saved on this machine only, not on GitHub (…). The next cosci write pushes it.

Times in turn headers use the timezone in your config.yml; see configuration.md.

The band

The band is the recording switch for the current thread. While it is open, every reply is recorded. While it is closed, nothing is appended.

cosci close-band
cosci open-band

cosci set-band open or cosci set-band closed does the same. There is no per-turn exemption. Only you change the band (see Permissions); if you ask the agent not to record something, it should tell you to close the band yourself.

The band belongs to one running session. It is a marker under discussions/.cosci-local/, which is never committed, so closing it in one window does not silence a session open elsewhere.

cosci quiet
cosci unquiet

These hide or show the commit footer for this session. Recording is unchanged.

Permissions

Each thread's permission file, discussions/<thread>/<thread>.meta.yml, decides what it may read and write. From the example run:

name: project-setup
home_repo: cosci-notes
permissions:
  cosci-notes: read-write
default_write: deny
participants:
- pats-claude-code
created: "Tuesday October 20 2026 \xB7 1:57 AM PDT"
status: active
turn_policy: linear

permissions maps a lab's key (the names under repos: in config.yml) to none, read or read-write. A lab not listed gets the thread_defaults of the lab the thread is stored in.

By default:

  • A thread stored in your private lab may write it, and may read every shared lab you have joined and the installed cosci code.
  • A thread stored in a shared lab may write it and read the cosci code. It can never read a private lab, so the agent there has no access to your private records.

Writes are denied unless the file allows them (default_write: deny). A write to a lab where the thread lacks read-write is refused, with nothing written. A read of a lab not configured on this machine, such as another person's private lab named by a locator, is refused with reason repo-not-configured; there is nothing to grant.

Only you type cosci close-band, cosci open-band (or cosci set-band), cosci grant and cosci share. The agent has no tool for them: it relays what you typed and is instructed never to issue one.

cosci permissions

This prints the thread's permission on every configured lab, and whether it is set in the file or inherited from a default. It changes nothing.

Several labs

You can join more than one shared lab; each is independent. The lab a thread is stored in decides what it may read:

  • A thread stored in your private lab reads your private lab and every shared lab you have joined.
  • A thread stored in lab A reads and writes lab A. It can never read a private lab. It cannot read lab B unless you type cosci grant lab-b read in that thread.
  • Nothing is copied between labs automatically. Content moves when you share it, when you grant a thread read-write on another lab, and through agents' notes about running cosci in a shared lab the thread may read.
  • Membership of lab A gives no access to lab B, and cosci never pools or syncs labs; GitHub access decides who can see each lab. Only someone who has joined both can grant a thread access to the other lab. What that conversation draws on can then appear in the labs it writes to, for their members to see. Lab A members who are not in lab B gain no access to lab B.

Search (cosci_search) covers every lab the current thread may read; repos=[...] narrows it. See the guide's Work with several labs.

cosci grant

cosci grant shared-repo read-write
cosci grant shared-repo read

cosci grant <lab> <none|read|read-write> edits the current thread's permission file and commits the change with a message naming the before and after state and who authorized it:

permissions: cosci-notes/project-setup - shared-repo read -> read-write (authorized by pat)

Granting a private thread read-write on a shared lab lets the agent write that thread's content there. Grant the narrowest access that works; none takes a grant back.

Two limits always hold:

  • No grant can give a thread stored in a shared lab any access to a private lab.
  • A thread cannot drop below read-write on the lab it is stored in.

cosci tidy lists every cross-repo write grant. It changes nothing unless you add --apply.

Recording things said elsewhere

cosci as kim: We agreed to use the DP1 alerts for the first pass.
cosci include-last 4
  • cosci as <handle>: <message> records one human turn in that person's words, verbatim, for a decision made in a meeting or another window.
  • cosci include-last <N> adds the last N turns of this session from before recording started, when the agent can supply that history.
  • cosci include-from "<phrase>" does the same from the turn that contains the phrase.
  • cosci log-as <name> starts recording the current exchange as a new thread.

The knowledge base

Each lab also keeps a knowledge base: an outline of topics and ideas with statements under them, stored as events under ledger/brain/.

Each statement links to where it was said with a locator such as cosci-notes@1c4444f97fe4:discussions/project-setup/project-setup-0.md#t2~14bb2b8580bc, naming the lab, commit, file and turn. It also says whose words it rests on: "pat's words", "confirmed by pat", or "inferred from pat's words". Statement ids start with the lab's key (cosci-notes/project-setup/priors-in-config-yaml), so different people's knowledge bases never collide.

When a thread opens, the agent receives the outline from every lab the thread may read, from each root down to what this thread touches, including open tensions. A statement whose source the reader cannot open is left out.

Before reading, cosci fetches each readable lab, at most once a minute, to see what others pushed. A lab it could not fetch is read from disk and named in the reply's not_fresh.

An agent about to act on something only inferred, where another reading would change what it does next, asks you in one line. Your answer is recorded as confirmation or correction.

/cosci:context where are the lens-model priors set?
/cosci:search ANTARES; alert stream

A background job learns your private knowledge base from your threads with your own claude or codex command; configuration.md says what it runs, how often and what it costs.

A shared lab's knowledge base learns from the lab's own threads, including what members share there, and from agents' notes about running cosci. Nothing from your private knowledge base reaches it unless you share it.

Notes about running cosci

Each shared lab also holds "What agents have learned about running cosci": how cosci, Claude Code and Codex behave in each environment, version by version. Agents read it before experimenting and add to it with cosci_observe; you can prompt one with /cosci:observe <finding>.

This is the one write an agent makes outside the lab its thread is stored in without a grant. It is narrow:

  • A finding goes under that root only.
  • It comes from a thread that may read that shared lab.
  • It is written as by "claude-code-agent" or "codex-agent", never by a person.
  • It is refused when its text names you or another configured person, a private lab or thread, or your home folder, or when it cites a locator.

Sharing

You can share anything from your private lab with a shared lab: a note in your own words, an excerpt of a thread, an idea from your knowledge base, or a single statement. In the CoSci window, what you share lands as your post in a lab thread you choose; the lab's members and their agents read it there, and the lab's knowledge base learns from it like any other conversation.

Nothing leaves your private lab until you share it, and it goes only to the lab you choose. Before anything that looks private leaves (a person's name, a private lab or thread name, your home folder, a link into your private lab), the window warns you first, and cosci share refuses it.

cosci share

In a session, cosci share shares statements from your private knowledge base:

cosci share cosci-notes/project-setup/priors-in-config-yaml

The statement is copied into the lab's knowledge base, with the passage it came from, so the lab's agents can see its source without opening your private lab. The agent may suggest something to share, naming the id (from the outline) and what the lab would see, but only you type the command. (A thread you grant read-write on a shared lab can also write its conversation there; see cosci grant.)

  • The copy records the sharing as your act ("pat's words") and keeps the links back into your private lab, which only you can open.
  • The lab gets one push of two commits: the passage first, then the statement that points to it, because a link names a commit that already holds its text. Your private lab keeps a line saying what you shared, when and where.

cosci share rules:

  • Type it in a thread stored in your private lab.
  • You need to have joined a shared lab. --to <key> names it, for example cosci share <id> --to lab-b. You may leave it out only when you have joined exactly one shared lab; with several, cosci refuses and asks you to name one.
  • It refuses any statement whose text names you, your home folder, or a private lab or thread. Nothing is shared by halves: if one statement is refused, none is shared.
  • Sharing the same statement again changes nothing, and says so.
