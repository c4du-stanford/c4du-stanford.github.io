Install

Architecture

The map of cosci, the code behind CoSci, for people who change it: modules, files on disk, permissions, GitHub sync, and how the knowledge base learns and shares statements. A private lab is a data repo with layer private; a shared lab is one with layer shared.

Where this page and the code disagree, the code is right. CONTRIBUTING.md in the cosci repository (not in an installed harness) covers the tests and checks.

What runs where

cosci is a local stdio MCP server plus a launcher, run by each person on their own machine around their own agent CLI, logged in as themselves. There is no cosci service or account.

 person ── types ──▶ Claude Code  or  Codex            (started by `cosci` / `cosci codex`)
                       │  stdio JSON-RPC, one server process per session
                       ▼
                 mcp/server.py      CcmSession: the current thread, the cosci_* tools, cosci_dispatch
                       │ imports              ▲ hooks, tools, instructions
                       ▼                      │
                 ccm_core (core) ── extensions ── ccm_core.brainops (knowledge base)
                       │                                  │
                       ▼                                  ▼
        clones under ~/.cosci-data/<owner>__<repo>  ⇄  GitHub, with the person's own git credentials

 Claude Code only:  tools/capture_hook.py on SessionStart, UserPromptSubmit, Stop, StopFailure, SessionEnd
 In the background: tools/brain.py learn --home <repo>, detached, running `claude -p` or `codex exec`

The launcher (ccm_core/cli.py, via bin/cosci) attaches all this to a session. For Claude Code it writes ~/.cosci/run/mcp-<pid>.json, harness-<pid>.md and settings-<pid>.json, passes them with --mcp-config, --append-system-prompt-file and --settings, and passes the skills with --plugin-dir ~/.cosci/plugin. For Codex it passes the server and the prompt as -c mcp_servers.cosci.* and -c developer_instructions=....

It writes nothing under ~/.claude or ~/.codex, and no .mcp.json, CLAUDE.md or AGENTS.md. Codex reads hooks only from ~/.codex, so Codex sessions have no capture hooks and record turns through cosci_append alone (cosci status says so). The next launch removes run files of exited sessions.

The server's environment: COSCI_CONFIG (the local ~/.cosci-data/config.yml), COSCI_HANDLE (the agent handle, <login>s-<harness>), COSCI_HUMAN_HANDLE, COSCI_HARNESS, COSCI_HARNESS_REF, COSCI_ROOT, COSCI_REPO (the default repo for a new thread), COSCI_LEARN and COSCI_LEARN_LOG. COSCI_NO_PULL=1 and COSCI_NO_PUSH=1 keep it offline.

The extension point

The core never imports the knowledge base: tests/test_core_extras.py (test_the_core_never_imports_a_brain_module) parses the core modules, mcp/server.py and tools/capture_hook.py and fails on any such import. The core calls named hooks in ccm_core/extensions.py; with nothing registered each does nothing, so the core behaves the same with or without the knowledge base.

 core call site                         hook               knowledge-base function (ccm_core/brainops.py)
 engine.bind / new_thread / catchup ──▶ bind_context   ──▶ outline and recent statements into the payload
 engine read paths                  ──▶ turn_locators  ──▶ a locator on every returned turn
 cosci_read(locators=[...])           ──▶ read_locators  ──▶ cited passages, through the permission check
 engine.append                      ──▶ citation_check ──▶ unresolved citations named in the footer
 capture_hook UserPromptSubmit      ──▶ prompt_context ──▶ lines about the current thread for the prompt
 server, after a call on a thread   ──▶ after_call     ──▶ maybe start background learning
 cosci_status                         ──▶ status         ──▶ the last learning pass
 cosci_dispatch "cosci share ..."       ──▶ promote        ──▶ sharing a statement

The knowledge base also adds MCP tools (register_tool; names start with cosci_) and a paragraph of server instructions (register_instructions). extensions.load() imports ccm_core.brainops once. The server and capture hook call it at startup; the engine never does.

A hook that raises never fails its call: extensions.call returns the error and callers report it in their payload (context_unavailable, hook_errors). A knowledge-base module that fails to import appears in cosci_status (extension_errors). promote (behind cosci share) is the exception: the server calls it directly, so a refusal reaches the person as an error.

A data repo holds no machine paths; those are all in ~/.cosci-data/config.yml. Graph events are named by their content, so logs from several machines merge as a set and any subset rebuilds the same graph.

Locators

Every citation is a locator naming a passage at a git revision. Code checks that it resolves and that any quote is in the passage; the reading agent judges whether it supports the statement.

<repo>@<rev>:<path>#t<index>~<digest>    one turn of a thread chunk; index counts turn headers from 0
<repo>@<rev>:<path>#L<a>-<b>~<digest>    lines a to b of any other text file
<repo>@<rev>:<path>~<digest>             a whole file (a shared statement's copied passage, understandings)

e.g. notes@1c4444f97fe4:discussions/project/project-0.md#t2~14bb2b8580bc

<repo> is the repo's config key, <rev> the first 12 hex digits of the commit, <digest> the first 12 of SHA-256 over the normalised text.

A GitHub repo's key comes from its name and is the same on every machine (owner/shared-repo is shared-repo). When another configured repo holds that name, a private newcomer gets owner__shared-repo and a shared newcomer is refused (shared_clash in ccm_core/remote.py), since a shared lab needs the same key everywhere. A configured key never changes; renaming one breaks its citations.

Graph ids are namespaced the same way, so different people's graphs never collide when read together. Topics are topic:<repo>/<slug>, statements are <repo>/<slug>/<entry-id>, and ideas are idea:<repo>/....

Permissions and repo types

Every repo in the config has a layer: private (one person's private lab), shared (a shared lab) or harness (the installed cosci code, the manager entry).

Every thread is stored in one repo and has a descriptor. The permission check in ccm_core/config.py decides each read and write for MCP, the hooks and tools/thread.py.

Thread stored inits own labanother private laba shared labthe harness
a private labread-writenonereadread
a shared labread-writenever, whatever any grant saysnone unless grantedread

Protections, innermost first:

  1. Default-deny writes. check_write passes only on an effective read-write. defaults.default_write is deny, and the harness check fails a template that differs.
  2. The descriptor. <thread>.meta.yml holds explicit permissions; without one, defaults come from its repo's thread_defaults. Only cosci grant, typed by the person and executed by cosci_dispatch, changes it. No agent tool grants, and the grant skill carries disable-model-invocation: true.
  3. The private-lab rule. layer_forbids: a thread stored in a shared lab has no access to any private lab, and nothing overrides that. new_thread and grant refuse such a request loudly.
  4. Knowledge-base reads. Every read goes through a Reader holding only the repos the current thread may read. A node whose citations the reader cannot resolve is dropped. A locator into a repo not configured here is refused with repo-not-configured, with no grant offered. Another person's private lab is reachable only through what they share.
  5. Writes into a shared lab from a private context. cosci_observe and cosci share refuse text holding the person's handles, home folder, or a private lab or thread name (graph.private_words_for); cosci_observe also refuses locators.
  6. Housekeeping. cosci tidy writes only clone-local state or files inside the repo being tidied, reading descriptors across repos only to report write grants.

A refusal raises PermissionDenied with the thread, repo, operation, permission held, reason and remedy. Nothing is skipped silently.

Sync

A clone caches its GitHub repo; the remote is the truth.

Network calls. Every fetch and push goes through engine.run_git_network (or publish._git), with a timeout, GIT_TERMINAL_PROMPT=0, stdin closed and no controlling terminal, so nothing stops at a credential prompt. GIT_ASKPASS and SSH_ASKPASS stay as the person has them, and cosci never asks for, passes, stores or embeds a credential. A timeout is reported as exit code 124.

Freshness. Orientation calls (opening a thread, status, list, digest, dispatch name resolution) run repo_freshness: fetch origin (15 s), then compare.

  • Behind only: fast-forward under the repo lock.
  • Ahead and behind: _rebase_diverged replays local commits onto origin when the tree is clean; an aborted replay leaves the clone as it was.
  • Anything unhealable (a fetch or auth failure, a diverged clone that cannot be replayed, an unreadable history) raises FreshnessError with an error code, auth_ok and a hint. A stale answer is never served silently.

The harness entry is only fast-forwarded. A repo with no origin is local-only and skipped.

Fresh reads. Knowledge-base reads (the context sent when a thread opens, cosci_context, cosci_search, cosci_open, cosci_read by locator, the prompt context) freshen every repo the thread may read, at most once per 60 s per clone (COSCI_FRESHEN_EVERY), within one fetch timeout for all, and never fail. A repo that could not be updated is read as it is and named in not_fresh. This is how what one person shares reaches another on their next read.

Writing. Freshness runs before the write takes the repo lock, never inside it (the lock is not re-entrant). The lock is an flock on cosci-write.lock in the clone's git common directory (shared by worktrees), with a 30 s timeout (LockTimeout).

commit_and_push commits only its own paths (git commit -- <paths>) with the person's git identity, raising GitIdentityError before writing anything when there is none. It restores the working tree if the commit fails.

Pushing. _push_with_retry tries up to 4 times. On a non-fast-forward it fetches and replays the local commits onto origin (replay_onto). When two machines append turns to the same chunk, merge_appended_chunk keeps both sides' turns and telemetry sidecars merge by turn hash, with no conflict. Any other conflict aborts the replay, leaves the clone as it was, and raises GitSyncError (push-rebase-failed) with a hint.

 append ─▶ freshen ─▶ lock ─▶ write chunk + sidecar ─▶ commit -- <paths> ─▶ push
                                                                      │
                     rejected (non-fast-forward): fetch, replay, retry (≤ 4)
                     refused or failed: commit stays local, sync.pushed = false

Not pushed. When the push fails after the commit, the turn stays committed locally and the result has sync: {pushed: false, reason, hint, note}. The footer gets a second line, → not pushed yet: saved on this machine only, not on GitHub (...). The next cosci write pushes it, and replies carry not_pushed while the clone is ahead. The next write or retried append pushes it (_push_if_ahead).

Knowledge-base publishing. Learning, outlines, CLI-written understandings and cosci share publish with publish.commit_files, which builds a commit from a throwaway index on origin's default branch and pushes it directly (retried up to 3 times). It never checks out, resets or sweeps in a session's working tree.

A file that another writer changed since it was read stops the publication (check_publication, code concurrent-update). Nothing is overwritten, and the local clone catches up at its next fast-forward. Without an origin, the commit goes on the local branch under the repo lock and only the committed paths are written to the working tree.

cosci_align, cosci_understand and cosci_observe from a session use the ordinary locked commit_and_push.

Background learning

 any cosci_* call on an open thread (online) ─▶ after_call ─▶ start_learning(home repo)
     off? (learn: off, or the CLI is missing)  ─▶ state off
     started < 30 min ago?                     ─▶ state due
     lock held by a running pass?              ─▶ state running
     else: spawn  python tools/brain.py --config <cfg> learn --home <repo> --by <handle>   (detached)
                  └─ learn_once ─▶ learner (claude -p / codex exec) ─▶ _check_delta ─▶ publish one commit

The trigger runs after every tool call on an open thread in an online session. It returns at once and never fails or delays the call; a failure to start goes to discussions/.cosci-local/learn-background.log. It starts at most once per 1800 s per repo (COSCI_LEARN_EVERY), and the child holds learn-background.lock until it exits, so passes never overlap.

The learner is the person's own agent CLI, chosen by the local learn setting: claude, codex or off (unset means claude when it is on PATH).

claude runs as claude -p --output-format json --tools "" --strict-mcp-config --no-session-persistence --settings '{"disableAllHooks": true}' with the prompt on stdin, in an empty temporary folder, so it can read and change nothing and none of the person's hooks sees their private turns. codex runs as codex exec --json --ephemeral --sandbox read-only. Both run under a time limit that grows with the prompt.

A pass reads only its lab's own turns since its read-through mark and learns into that lab's graph. Code keeps only what it can check:

  • Sources resolve.
  • Quotes are in their passages.
  • by names who said a quoted turn.
  • Aims, instructions and requirements quote a human turn.
  • An update never changes what was said or who said it.
  • There is one change per entry per reply.

The rest is dropped and counted. What holds becomes graph events and new read-through marks, published in one commit. The outcome (off, nothing-new, learned, error) is kept in learn-state.json for cosci status and cosci_status. Failures also go to COSCI_LEARN_LOG. Outlines and understandings come only from the command line (tools/brain.py outline, understand).

Sharing

cosci share (threads.md) shares statements from a private knowledge base with a shared lab. The person types cosci share <statement-id> ... and cosci_dispatch executes it; no agent tool does. Inside, the action kind, the functions (brainops.promote, publish.promote), the graph events and the file names call it a promotion.

 private lab (the current thread's)                    shared lab
 graph: notes/project/priors-in-config ──┐
 cited turn notes@<rev>:...#t2~<digest> ─┤  commit 1: ledger/brain/evidence/<digest>.md (the passage it came from)
                                         └▶ commit 2: topic, assertion (provenance: the private id and locators),
                                                      `about` relation, `stated` act by the person who shared it,
                                                      `justify` pointing to the passage copy
                                            both commits reach origin in one push, or neither does
 ledger/brain/promotions.jsonl ◀── a line saying what was shared, committed and pushed afterwards

cosci share requires:

  • The current thread is stored in a private lab.
  • The statement exists and is live in that private graph.
  • A shared lab the thread may read (--to when there are several).

If any text, the statement or its passage, holds private words, the whole command is refused, so nothing is shared by halves. The copy keeps the quoted words with up to 1500 characters on each side. Sharing a statement already shared writes nothing and says so. The private locators are kept as provenance for the person who shared it. Nobody else can resolve them, so they are not premises.

Notes about running cosci

Agents record what they learn about running cosci and the agent CLIs beneath it with cosci_observe: which version of which agent CLI did what, in which environment, and where cosci got in the way. A finding goes to a shared lab as graph events under the root idea:<shared>/cosci only, as an observed act by <harness>-agent on a named version. No person writes or approves it; a later finding supersedes or contradicts it.

It is the one agent write outside the thread's repo without a grant; threads.md lists its limits. These findings are the first place to look when triaging a problem with cosci (triage.md).

The harness under git

The installed code, skills and prompts at ~/.cosci are a local git repository. Each release is one commit on base, tagged base/<version>; main is base plus the person's own mutations (harness.md).

A person can try changes to how agents work on one machine, affecting nobody else: edit a skill or the prompt wording, run the harness check, tag it, run a session from the tag with cosci --harness <name>, and compare against base. cosci improve drafts such changes from the record on a branch improve/<time> (improve.md).

The rules are in mutable-surface-manifest.md. The agent never applies a change on its own, the harness check must pass, and the person commits with cosci harness tag <name> --as <handle>. The never-touch check fails when the engine's write path, the harness check itself, the tests, turn telemetry, the interpreter floor or the governance docs differ from the base release, so those change only upstream, in this repository, through a release.

The harness repository has no push remote (every push URL is disabled), so a mutation never leaves the machine. A change worth keeping for everyone comes back here as an ordinary commit with tests.
