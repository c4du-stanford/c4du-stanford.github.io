cosci triage

--- title: "cosci triage" status: active tags: [cosci, governance, triage] last_updated: "2026-10-20" ---

How to classify a problem with cosci, decide whether it leads to a change, and where and in what order to make it. mutable-surface-manifest.md says what may change.

Does a problem lead to a change?

Answer these in order. At a No, stop: the problem stays recorded as a finding or thread turn.

  1. Recurrence. Has it happened at least twice, or can one occurrence do unbounded damage (a credential exposed, the record corrupted, private text reaching a shared repo)? One-off friction is noise.
  2. A bounded target. Is there a specific edit likely to stop it, in a may-touch file of one person's harness (skill or prompt wording, style.md) or in the cosci repository (the never-touch list and every code fix)?
  3. A named verifier. Does a check show the fix worked: a test, a harness check, a telemetry flag that should stop appearing? In the cosci repository, a test that fails before the fix.
  4. Cost of being wrong. Can it be undone? cosci harness use <previous ref> undoes a harness change; the next release undoes a release. An irreversible change is discussed with the people affected first.

Where the change is made

  • One person's harness. The person decides the edit, the agent applies it under ~/.cosci on their instruction, the check runs, and the person commits with cosci harness tag <name> --as <handle>. cosci improve can draft such edits from the record on a branch improve/<time> for the person to adopt with cosci harness merge (improve.md). They can try it for one session with cosci --harness <name> before making it current. Only one change is pending at a time (cosci harness pending): the harness has one working tree. It never leaves that machine.
  • The cosci repository. An engineer makes the change with a test and both checks passing (CONTRIBUTING.md at the cosci repository's root). It reaches everyone in a release through cosci update. A harness change worth sharing goes this way too.

Order of work

Rank survivors by severity × frequency ÷ blast radius:

  • Severity. S1 a credential exposed or private text in a shared repo. S2 the record's integrity (a lost, duplicated or misattributed turn). S3 wrong published knowledge-base content (a citation that does not hold, or a wrong standing: how well supported a statement is). S4 cost, latency or protocol friction. S5 style and readability. Style is last: most frequent, least costly each time.
  • Frequency. Occurrences per 100 recorded turns over a recent window.
  • Blast radius. How many files, people and agents the change affects; smaller first at equal severity and frequency.
  • Ties. A reported incident before a telemetry pattern; a quicker verifier before a slower one.

Changing this page

As with the manifest, an engineer changes this page in the cosci repository with the reasoning in the commit message. An agent may cite it and ask for a change in a thread.
