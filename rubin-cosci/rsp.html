Install

Rubin Science Platform

You can run cosci in a terminal of the Rubin Science Platform's Notebook aspect (JupyterLab), next to your data. You upload the installer, run it in a terminal and answer its questions. It can install Claude Code or Codex in your home directory and sign you in to them, sign you in to GitHub, and join your lab. Every sign-in works with a code or a link you open in your own browser, so nothing needs a browser on the platform itself.

If you prefer to set up the agent and git's access to GitHub yourself (an SSH key or a token), or to install with --yes, see Setting things up yourself.

What has been tested, and what has not

Tested end to end on a Linux HPC login node (RHEL 8) with Claude Code 2.1.304 (native installer, ~/.local/bin), Python 3.11 (the full test suite also passes on 3.9), and HTTPS git with the person's own credentials against real private GitHub repos. Install, a recorded session, background learning, sharing a statement with a lab, a second person's reads, the slash commands, the Codex attach (without a model call) and uninstall all worked. That environment resembles an RSP terminal: a Linux shell, a persistent home directory, no root, and software you install under ~/.local.

The RSP itself is untested; the RSP-specific notes below (the stack's Python, the sign-ins, what persists, outbound SSH) are expectations. Record what happens with /cosci:observe in your session (in Codex, ask the agent to record a cosci finding), for example:

/cosci:observe Claude Code 2.1.x on the Rubin Science Platform: the guided install put claude in ~/.local/bin and its sign-in link worked from my browser; CoSci's Python environment was made from the stack's python3; the GitHub device code sign-in worked

Findings go to "What agents have learned about running cosci" in your shared lab, which every member's agent reads before experimenting. Record failures too, and how you got past them.

1. Get the installer and open a terminal

On your own computer, open the install page, https://c4du-stanford.github.io/rubin-cosci/install/, and click Download for the RSP or Linux. You sign in to GitHub to open the page (Stanford members sign in with Stanford); if it shows 404, ask the person who invited you to add your GitHub account. The download is cosci-install.sh, one file with CoSci inside.

Upload it into JupyterLab: drag the file into the file browser on the left, or use its Upload button. It lands in your home directory.

In JupyterLab, open the Launcher (the + tab) and choose Terminal. Run everything below there.

2. Check Python and git

python3 -c "import sys, venv; print(sys.executable, sys.version.split()[0])"
git --version

The terminal's python3 should be the stack image's Python, 3.9 or newer. cosci makes its own Python environment from it, ~/.cosci/venv, and installs the packages it needs there, so the stack's Python is not changed. That needs Python's venv module, which the first line checks. If import venv fails, set COSCI_PYTHON to a Python that has PyYAML (see the install reference).

3. Run the guided install

bash ~/cosci-install.sh

The release is inside the file, so the install downloads nothing of CoSci's own and needs no GitHub credentials on the platform. The installer checks the release's SHA-256 checksum and refuses to install on a mismatch (a file cut short while uploading: upload it again).

The installer then asks its questions, described in the guide. Press Enter to take the default shown. On the RSP:

  • A look at this computer. The system line should end with this is the Rubin Science Platform. Nothing is changed at this step.
  • A coding agent. Choose Claude Code, Codex or both. For each one it offers to install it with its maker's installer, which needs no root and puts the command in ~/.local/bin, then to sign in with your own account (a Claude account for Claude Code, a ChatGPT account for Codex). Claude Code's sign-in (claude auth login) prints a link: open it in your browser, sign in and paste the code back into the terminal. Codex's (codex login --device-auth) shows a link and a code: open the link in your browser, sign in and enter the code. The agent keeps the sign-in in your home directory; CoSci never sees it.
  • GitHub. Say yes to using shared labs now. With no gh on the platform, the installer offers a private copy in ~/.cosci/gh (no root needed), checked against GitHub's published checksum. gh then shows a one-time code: open https://github.com/login/device in your browser, paste the code and click Authorize. Where there is no system keychain, as is likely here, gh keeps the sign-in in a file in your home directory (~/.config/gh/hosts.yml) and says so. Anyone who can read your home directory, including the platform's administrators, could read it. Answer no to Also use it for your other git work on GitHub? (the default) to keep the sign-in for CoSci's labs only.
  • Lab to join. Type your lab's repo as OWNER/SHARED-REPO. The installer checks your access right away; if the lab's owner has added you, it can accept the waiting invitation for you. If it says your account can't see the lab, ask the owner to add you, or accept the invitation at https://github.com/notifications, and type it again. To start a new lab instead, press Enter and answer yes to Do you want to start a new shared lab?.
  • Your private lab. On this computer means your RSP home directory, which persists across lab sessions. Choose GitHub to keep it in a private repo on your account instead.
  • Your PATH. Say yes to add ~/.local/bin (it holds claude and cosci) to your PATH in ~/.bashrc. Then open a new terminal, or run source ~/.bashrc.

OWNER/SHARED-REPO stands for your shared lab's repo; use your own names. Before Go ahead? the installer shows the same choices as options; keep them if you want to install the same way again with --yes.

cosci commits under your git name and email when they are set (git config --global user.name "Pat Example" and git config --global user.email pat@example.org); otherwise it picks one for its own repos and the summary shows it.

The summary should match the guide. Then start a session with cosci and type /cosci:start. Later, cosci update fetches newer releases through git with your GitHub sign-in (the same access the install page needs). If your GitHub access on the platform reaches only your lab (for example a token limited to it), or the update can't reach the release, download the newest cosci-install.sh from the install page, upload it and run it; your labs and settings are kept.

Setting things up yourself

Follow this instead of the questions if you prefer to install the agent yourself, to give git its own way to reach GitHub, or to install with --yes (for example from an agent or a script, where the installer asks nothing).

Install Claude Code

Claude Code's native installer needs no root and installs claude in ~/.local/bin:

curl -fsSL https://claude.ai/install.sh | bash

Put ~/.local/bin (it holds claude and the cosci link) on your PATH in every new terminal:

echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc
claude --version

Run claude once to sign in with your own Claude account. In a browser-only terminal it prints a URL; open it in your browser, sign in and paste the code back.

Give git a way to reach GitHub

cosci never prompts for a password, so git must reach your private lab and your shared lab's repo on its own. Set up one of these and check with git ls-remote.

An SSH key. Make a key, add the public half to your GitHub account (Settings → SSH and GPG keys) and test it:

ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519 -C "rsp"
cat ~/.ssh/id_ed25519.pub
ssh -T git@github.com

Then install cosci with --protocol ssh.

A key without a passphrase works everywhere, but anyone who can read your home directory can use it. A key with a passphrase must be loaded into an agent (eval "$(ssh-agent)"; ssh-add) in each new terminal before you start cosci, which cannot answer a passphrase prompt.

If outbound SSH on port 22 is blocked, GitHub also accepts SSH on port 443; add to ~/.ssh/config:

Host github.com
  Hostname ssh.github.com
  Port 443
  User git

HTTPS with a personal access token. Create a fine-grained GitHub token limited to your private lab's repo and your shared lab's repo, with read and write access to their contents, and choose how git keeps it:

  • git config --global credential.helper store writes the token in plain text to ~/.git-credentials in your RSP home directory, where it persists across sessions. Anyone who can read that directory, including the platform's administrators, can read the token: use this only if that is acceptable, with a narrowly scoped token.
  • git config --global credential.helper 'cache --timeout=28800' keeps it in memory for eight hours. In each new lab session, run one git command by hand (for example git -C ~/.cosci-data/pat__cosci-notes fetch), type the token when asked, then start cosci.

This must work before you install:

git ls-remote https://github.com/OWNER/SHARED-REPO HEAD          # or git@github.com:OWNER/SHARED-REPO.git with SSH

pat is an example login; use your own.

Install cosci with options

bash ~/cosci-install.sh --yes --shared OWNER/SHARED-REPO --private pat/cosci-notes --handle pat
  • --yes asks nothing; leave it out to be asked only the questions these options do not answer.
  • Add --protocol ssh if you set up SSH.
  • Use --create-private in place of --private to have the installer create your private lab on GitHub (default <login>/cosci-notes), or leave both out to keep it in your home directory.
  • To start a new lab, the first member uses --create-shared OWNER/SHARED-REPO in place of --shared, then gives the others write access on GitHub (cosci sends no invitations); they use --shared. See Start a new lab.
  • Leave out --shared if your project has no shared lab yet. The summary then shows shared none yet; join it later with cosci join OWNER/SHARED-REPO and start a new session.

Creating a repo on GitHub (--create-private, --create-shared) needs the GitHub CLI (gh), signed in with gh auth login.

With read access to the cosci repo you can install from a clone: git clone https://github.com/c4du-stanford/rubin-cosci ~/.cosci-src (or git@github.com:c4du-stanford/rubin-cosci.git with SSH), then ~/.cosci-src/install.sh with the same options. cosci update then follows the release tags.

What persists, and what does not

Your home directory persists across lab sessions and image changes, and with it:

  • the cosci harness (~/.cosci), with CoSci's own Python environment (~/.cosci/venv) and, if you chose it, its copy of the GitHub CLI (~/.cosci/gh)
  • your data repos and configuration (~/.cosci-data)
  • the source clone (~/.cosci-src), after a clone install
  • ~/.local/bin/claude and ~/.local/bin/cosci
  • Claude Code's and Codex's own settings and sign-ins (~/.claude, ~/.codex)
  • the GitHub CLI's sign-in (~/.config/gh)
  • your git configuration, keys and any stored token

The stack image's software changes when you pick another image. cosci runs with its own Python environment, made from the stack's python3 when you installed. After an image change that environment may no longer run. If cosci then fails to start, run the installer again (bash ~/cosci-install.sh): it makes the environment again when the old one no longer runs. Run the step 2 check if anything looks wrong.

A running session ends when your lab shuts down (for example when idle). Recorded turns are committed in your clone; unpushed ones go to GitHub with your next cosci write. An ssh-agent or cache credential helper also ends with the lab; load the key or prime the cache again next session.

Codex

Codex on the RSP is untried. The guided install offers to install it and sign you in with codex login --device-auth; or install it into your home directory yourself, sign in and check codex --version. Start sessions with cosci codex. Record what you find, as above.
