Install

The harness

Everything that shapes an agent session: the cosci runtime (engine, MCP server, tools), the skills, and the prompt text added to the system prompt. It lives at ~/.cosci, a local git repository that is never pushed; every release and change is a commit. Your data repos sync with GitHub.

Model

baseBranch base holds the releases, one commit each, tagged base/<version>. Never edited by hand.
current harnessBranch main: base plus your changes. cosci runs it by default.
tagged harnessescosci harness tag <name> commits the current harness and tags it harness/<name>.
branchescosci harness branch <name> starts a separate line of changes; cosci harness use <ref> switches the current one.
any version, on demandcosci --harness <ref> runs one session from a tag, branch or commit (its code, skills and prompt) without changing what is current.

Layout (the same at every version):

~/.cosci/
├── ccm_core/      engine, knowledge base, CLI, harness management
├── mcp/           the cosci MCP server
├── skills/        the /cosci:* skills
├── tools/         the capture hook, the knowledge-base tool, the check, lint and repair tools
├── harness/       prompt text per agent: claude-code.md, codex.md
├── templates/     config, style and learning-prompt templates
├── docs/          these pages
├── bin/cosci        the launcher
└── VERSION, install.sh, uninstall.sh, ccm_pyfloor.py, README.md

Runtime state (settings.json, run/, plugin/) is git-ignored and not part of the harness.

cosci adds harness/claude-code.md to Claude Code's system prompt (--append-system-prompt-file) and passes the skills as a plugin (--plugin-dir). cosci codex passes harness/codex.md as developer instructions (-c developer_instructions=...); Codex has no per-session skills, so its prompt has the agent relay the cosci <verb> commands you type. Each prompt must stay within 6144 bytes; the prompt-budget check fails a larger one.

Changing the harness: who may, and how

The rule, from mutable-surface-manifest.md: the agent never applies a change on its own. A change takes these steps:

  1. You decide on an edit.
  2. You or the agent, on your instruction, apply it under ~/.cosci.
  3. The check passes (cosci harness check).
  4. You commit it with cosci harness tag <name> --as <handle>, which reruns the check and names you in the tag.

triage.md says how problems are classified and when one becomes a change. cosci improve drafts changes from your recorded threads on a branch improve/<time> for you to try, then adopt or delete (improve.md).

cosci harness check                                    # the check: 11 checks over this checkout
cosci harness pending [--patch]                        # the applied-but-uncommitted edit
cosci harness tag <name> [-m "why"] --as <handle>      # check, commit, tag harness/<name>; refuses on failure
cosci harness discard                                  # drop an applied edit you are not keeping
cosci harness list                                     # current commit, branches, base releases, tags
cosci harness diff [<a>] [<b>] [--patch]               # two versions; with no args, current vs. base
cosci harness show [<ref>] [--agent codex]             # the prompt text at a version

The check covers:

  • Python and shell syntax
  • config template and skill front matter
  • that docs/commands.md matches the command table
  • doc links
  • each prompt's size and required passages
  • the skills' contract
  • skills coverage: every typed verb has a skill, every skill an argument-hint, and the band, grant, share and improve skills carry disable-model-invocation: true
  • the JSON-emitting helpers
  • token-shaped strings
  • that the never-touch files match base

The never-touch files are the check, the tests, the engine's write path, turn telemetry, the interpreter floor and the governance docs. If a harness changes one, the check fails and the tag is refused. They change in the cosci repository and arrive in a release.

Selecting

cosci --harness <name>              # one session from that version; current is untouched
cosci harness use <ref>             # make a tag, branch, or commit current for every session
cosci harness branch <name> [ref]   # new branch from the current commit (or from <ref>); edits now go there
cosci harness merge <ref>           # merge another harness into the current one (a real merge commit;
                                   # a conflict, or a failed check on the result, is undone and reported)

A --harness <ref> session runs from a worktree under ~/.cosci-data/harnesses/, so two versions can be compared side by side. Checking out a tag with use leaves the repo detached; run cosci harness branch <name> before further changes.

Updating

cosci update --check
cosci update [--to vX.Y.Z]

cosci update installs a newer release from where you installed:

  • Install from the install page: it fetches the release repo (stanford-developers/rubin-cosci-install) through git with your GitHub sign-in, and when its VERSION is newer than yours it runs that release's installer, which checks the release against its checksum. The repo holds only its newest release, so --to is refused. If it can't reach the repo, download the newest installer from the install page and run it; your labs and settings are kept.
  • Clone install: it fetches release tags into your clone and installs the newest, or the one --to names.

The release is committed on base, tagged base/<version>, and merged into the current branch; uncommitted edits are committed first. Your settings and data repos stay.

A conflicting merge is aborted: the new base is tagged, the current harness is unchanged, and the conflicting files are listed. Resolve it in ~/.cosci with git (git merge base, fix, commit), or run plain base for a session with cosci --harness base/<version>. Pushing is disabled for every remote of ~/.cosci.

Underneath

It is plain git: git -C ~/.cosci log --oneline --graph --all, git tag, git diff base..main and git worktree list show what the cosci harness commands report.
